Accounts & Sign-in

The single guide for creating every kind of account and verifying sign-in works. Do this before any other phase — every later guide assumes these accounts exist.

⚠️ What's stubbed in this flow
  • Invite emails are not sent. When Tia creates an invite, copy the link from the admin UI and paste it into a private window (or forward to the invitee) — that replaces the emailed link.
  • Resident self-signup does not require email verification during the pilot.
📋 Before you start

Device: 💻 Laptop for admin + signing up. 📱 Phone for operator once you've invited him.

Two paths — pick one:

  • Fast path (recommended): the dev team has already run npm run seed:pilot, which creates every account on the Test users card. Skip to § Verify the sign-in flows.
  • From scratch: if you want to walk through account creation yourself (e.g. to demo onboarding), follow § Manual account creation.

How each role is created

Three paths, depending on the role. This is just reference — you'll actually execute the scenarios below.

Role How they're created Why
Admin Dev team (one-time) via npm run seed:pilot. No admin exists yet to invite them.
Resident Self-signup from the public homepage. Residents are general public — anyone with a valid address in the pilot zone can join.
Operator Admin sends an invite; employee accepts at a one-time link. Employees — no self-signup, so random people can't give themselves driver access.
Depot worker Same invite flow, plus admin picks the depot.
Depot manager Same invite flow, plus admin picks the depot.

Verify the sign-in flows

Work through these five scenarios in order. If the pilot seed has already run, accounts are ready — you're just checking that each one logs in to the right area of the app.

Scenario 1 — Admin signs in

Admin Signed in as Tia · tia.admin@wbct-pilot.test.

  1. Open the homepage in your main browser.
  2. Click Sign in.
  3. Enter Tia's email and the password from the Test users card.
Expected: Tia is redirected straight to the admin dashboard (not the resident home). She sees KPI tiles and a left sidebar with Users, Zones, Pricing, Redemptions, Routes.

Verify:

Landing screen is the admin dashboard, not resident home

Admin sidebar is visible

Scenario 2 — Resident self-signup (email + password)

Resident In a private/incognito window.

This is the only scenario where you create a new resident on top of the seeded ones — useful for confirming the welcome bonus fires for a brand-new account.

  1. Open the public homepage in a fresh private/incognito window.
  2. Click Sign up.
  3. Enter a name, an email you control, a password, and a real street address in the pilot zone.
  4. Submit.
Expected: The new resident lands on the resident home screen with a 10,000-point signup bonus and a short 3-step onboarding card.

Verify:

Name appears correctly in the top-right menu

Points balance shows 10,000

Address is saved (check the Profile tab)

Scenario 3 — Resident sign-up with Google

Resident A different private window.

  1. Open the homepage.
  2. Click Sign up → Continue with Google.
  3. Pick a Google account.
  4. Fill in the remaining form fields (address, phone).
Expected: Same as Scenario 2 — lands on the resident home screen with 10,000 points. No password prompt.

Verify:

Google sign-in completes without asking for a password

Name (and photo, if the Google account has one) appear in the top-right menu

Scenario 4 — Operator cannot self-sign-up

Tester In a fresh private window, no one signed in.

  1. Open the homepage.
  2. Click Sign up.
  3. Look at the form. There should be no role picker or "I'm an operator" option.
Expected: No self-select for operator, depot, or admin. The only path to those roles is an invitation — tested in Scenario 5.

Verify:

No role selector anywhere on sign-up

Scenario 5 — Admin invites an operator, operator accepts

Admin + Operator Two browsers (one for Tia, one private for the invitee).

This scenario creates a brand-new operator alongside the seeded one — useful to confirm the invite flow end to end.

Admin side — send the invite

  1. Signed in as Tia, open /admin/invites (sidebar → Users & Invites).
  2. Click Send invite.
  3. Enter a throwaway email (one you control), pick role Operator.
  4. Click Send.
  5. The invite appears in the list with status pending. Click it to copy the invite link (email delivery is stubbed — you'll forward the link yourself).

Operator side — accept the invite

  1. Paste the link into a fresh private/incognito window.
  2. Click Accept invitation.
  3. Set a password and submit.
Expected: The new operator lands on the operator home screen (Today's Route), not the resident home. Opening the same invite link a second time reports "already used."

Verify:

The invite appears in Tia's list with status pending

New operator lands on the operator screen, not resident

Same link reused → "already used"

For depot-worker / depot-manager invites, a Depot dropdown appears (try it with a second invite)

Signing out

From any signed-in screen, open the top-right menu and pick Sign out. You should return to the public homepage. If you reload and still see the logged-in view, that's a bug.

Tip — one browser per role. Testing cross-role flows (admin invites → operator accepts → depot processes) is much smoother with one browser or private window per role. Don't sign in and out of a single window — you'll lose your place in the flow.

Manual account creation (optional)

Only follow this section if you're onboarding a client who wants to see the signup experience from scratch, or if the pilot seed hasn't been run. Otherwise skip it.

The first admin

The dev team creates the first admin via the pilot seed script. Ask for the email and password — nothing self-serve here, because there's no admin to invite them.

Keep the admin password somewhere safe. Every invite in the pilot flows from the admin account. Lose access and nobody else can create operators or depot workers until the dev team resets it.

A new resident (self-signup)

Same as Scenario 2 above. No invite required — just a real address in the pilot zone.

A new employee (operator / depot / manager)

Same two-step flow as Scenario 5. The Depot dropdown appears only for depot-worker and depot-manager roles.

Quick troubleshooting

What you see Probably because What to try
"This address is outside our service area" on sign-up The address's zip isn't in any pilot zone. Ask the dev team to add the zip to the zone list.
Google sign-in popup closes with no result Browser popup blocker or a third-party cookie setting. Allow popups for the site and retry.
Invite link says "invalid or expired" Already accepted, or past the 7-day window, or revoked. Ask Tia to send a fresh one.
Employee lands on the resident home after accepting Browser session cached before the role claim applied. Sign out, sign back in, refresh.
No Depot dropdown when inviting a depot worker No depots exist yet. Create one under Zones & Depots first.
Resident signs in and lands on the admin page (or vice versa) Role-routing bug. Write it down with the exact email used and send to the dev team.
