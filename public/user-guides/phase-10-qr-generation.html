Phase 10 · QR sticker generation

What Tia sees after Phase 9 lands: a new 🏷️ Bag stickers tab in the admin sidebar that pre-prints the QR sticker sheets the whole system relies on. Each sheet is 10 labels sized for a Rollo thermal printer, with a scannable QR plus a printed-number fallback. This is the fix for a bootstrap problem the earlier phases papered over: until now, sticker sheets only existed as physical paper; the app did not know about them until an operator scanned one at delivery. Phase 10 moves the QR codes into Firestore first, then prints them.

What you're verifying

  • Tia can generate a new sticker sheet with one click — the app picks a unique 4-digit sheet number and writes the stickerSheets + 10 bags records atomically.
  • The print view renders 10 labels, each with a QR code and the printed number (BAG-4237-01 through BAG-4237-10), sized for Rollo 2.25″×1.25″ thermal label stock.
  • Printing marks the sheet's printedAt timestamp so the admin knows which sheets are ready to hand to operators.
  • When Aguirre the operator scans the first sticker at delivery, the same 10 bag docs get claimed for the resident — no new bags created, no duplicates.
  • The admin list view correctly reflects each sheet's lifecycle: Awaiting print → Printed · unassigned → Issued.
Setup before you start. You only need an admin account signed in (Tia) to test most of this guide. To verify the end-to-end delivery handoff in Scenario 5 you'll also need a pending bag order on an in-progress route (same prerequisites as Phase 6). If you just want to sanity-check the print view, skip Scenario 5.
Scenario 1 — Generate your first sticker sheet

Admin Signed in as Tia on a laptop.

  1. Open /admin/bags (or click 🏷️ Bag stickers in the sidebar).
  2. Observe the three status tiles — Awaiting print, Ready to deliver, Issued. On a fresh install all three are 0.
  3. Click Generate new sheet. The button spins briefly, then the browser navigates to the print view for the new sheet.
Expected: A brand-new print view opens at /admin/bags/<sheetId>/print showing a #XXXX sheet number (4 digits) and 10 labels labelled BAG-XXXX-01 through BAG-XXXX-10. Under the hood the API reserved that sheet number, created the stickerSheets doc with residentId: null, and created 10 bags docs each with status: "unused" and residentId: null.

QR codes look like machine-readable squares, not a broken image

The printed number under each QR matches the same format BAG-XXXX-NN

The sheet number across all 10 labels is the same (e.g. all BAG-4237-*), index runs 01 through 10

Scenario 2 — Print the sheet

Admin On the same print view.

  1. Click Print + mark at the top of the page. The browser print dialog opens.
  2. In the dialog, verify the paper size shows as 2.25 × 1.25 in (or your browser's equivalent label preset).
  3. Choose Save as PDF for a first test so you can inspect the output without burning label stock.
  4. Open the saved PDF. Each of the 10 labels should occupy its own 2.25″×1.25″ page.
Expected: The browser sends 10 pages to the printer. The admin sidebar, the print toolbar, and the "Preview below shows all 10 labels…" note all disappear in the print output. After the print dialog closes, the page refreshes and the subtitle now reads "last printed <timestamp>". The Firestore stickerSheets doc now has a printedAt value.

Each label prints on its own page — no two labels share a sheet

The QR on each label looks dark and crisp in the saved PDF (not blurry or rasterized)

The subtitle flips from "not yet printed" to the printed timestamp after the dialog closes

Reopening the page the next day still shows the printed timestamp (persisted)

Scenario 3 — Read the admin list view

Admin Back to /admin/bags.

  1. Reload the page.
  2. The sheet you just printed should be the top row.
Expected: The row shows the sheet number (monospace), a sky-blue Printed · unassigned badge, an empty resident column, and timestamps in the Created and Printed columns. The top status tiles now show 1 in Ready to deliver and 0 in Awaiting print.

Generating a second sheet before printing it increments the Awaiting print tile to 1 and drops its badge to the amber Awaiting print pill

The Print view button on each row opens that sheet's print page directly

Sheets sort newest-first

Scenario 4 — Unique-number guard

Admin Rapid-fire test.

  1. Click Generate new sheet several times in a row (5–10 sheets).
  2. After each generation finishes, go back to /admin/bags and skim the Sheet # column.
Expected: Every sheet has a distinct 4-digit number. The API retries up to 8 times if it randomly lands on a colliding number. At pilot scale (a few hundred sheets) collisions will be rare; if you ever see a 503 response with sheet_number_exhausted, we've run out of the 9000-number space and the reservation scheme needs to grow to 5+ digits.

No two rows share the same Sheet #

Each sheet's 10 bag codes are unique across the whole bags collection

Scenario 5 — Operator claims the sheet at delivery

Admin + Operator Two devices (or two tabs).

This is the end-to-end handoff. It requires a pending bag order already enqueued on today's in-progress route — follow Phase 5 and Phase 6 to set that up if you don't have one.

  1. As Tia, grab one of the Printed · unassigned sheets from the list. Open its print view and note the first sticker's code, e.g. BAG-4237-01.
  2. As Aguirre the operator, start the route and navigate to the bag-order delivery stop for a resident.
  3. At the deliver step, scan or type BAG-4237-01 and submit.
  4. Switch back to Tia and reload /admin/bags.
Expected: The sheet's row flips to a green Issued badge, the Resident column now shows the receiving resident's name, and the Issued column fills in with today's timestamp. In Firestore, the same 10 bags docs that were created in Scenario 1 are still there — their residentId field changed from null to the resident's uid (no new docs, no duplicates). The stickerSheets doc also has residentId and bagOrderId set.

Bag count in Firestore's bags collection did not grow by 10 — the existing docs were updated, not recreated

Trying to re-deliver the same sheet to a different bag order returns sheet_already_issued

Scanning a sheet number that was never generated (e.g. BAG-9999-01) returns sheet_not_pre_issued

Scenario 6 — Resident scans a claimed bag

Resident Same resident the sheet was just delivered to.

  1. Open the resident app on the phone and go to /resident/scan-bag.
  2. Scan or enter one of the codes from the delivered sheet (e.g. BAG-4237-03).
  3. Complete the flow — declaration + doorstep photo → submit.
Expected: The pickup creates successfully. This confirms the delivery handoff is complete: the bag exists, belongs to this resident, and is in unused status ready to be claimed. Before Phase 10 this worked too, because the deliver endpoint created the bag docs on-scan; after Phase 10 it still works, because the same docs are claimed instead.

Scanning a sticker from a sheet that was never delivered returns bag_not_yours (the bag has residentId=null; the resident is not null; inequality rejects)

Scanning a sticker from another resident's delivered sheet still returns bag_not_yours

Quick troubleshooting

What you see Likely cause What to try
"Generate new sheet" errors out with sheet_number_exhausted The 1000–9999 space has enough collisions that 8 retries in a row all hit existing sheets. Only realistic after thousands of sheets. Outgrow the 4-digit scheme — widen SHEET_NUMBER_MAX in /api/qr-sheet/route.ts to 99999.
QR codes render as plain text or a broken <svg> qrcode server render failed silently or the SVG markup is being stripped. Check the print-view server logs for an exception from QRCode.toString. Confirm the dependency is installed and the route runs in nodejs runtime, not edge.
Print output cuts off or is wildly the wrong size The browser ignored the @page 2.25 × 1.25in size and defaulted to Letter. In the print dialog, under More settings, set paper size to a custom 2.25 × 1.25 inch or pick the Rollo preset. Some browsers need "Save as PDF" to honour custom @page sizes.
Operator scan returns sheet_not_pre_issued on a sticker you just printed The printed label is reading as a different sheet number (e.g. smudged scan) or the sheet was deleted from Firestore. Type the printed number manually instead of scanning — if the typed code works, the camera misread the QR. If typed also fails, verify the stickerSheets doc still exists.
Row shows Printed · unassigned but Tia never clicked Print The Print + mark button also fires when Tia uses the browser's own print shortcut on the preview page, as long as the endpoint call succeeds afterward. No action needed — this is intentional so the printed timestamp reflects the latest actual print attempt.
Admin list view is empty even though API calls succeeded The page is server-rendered — its cached version may be stale. Reload the tab. It's already force-dynamic, so a reload is enough; no deploy needed.

What's not testable yet

Phase 10 only covers generating stickers. Bulk-printing N sheets at once, re-printing a subset of labels from an existing sheet, voiding a sheet that got damaged, and integrating a real Rollo driver (vs the browser print dialog) are all future work. The sheet-number space is also deliberately small (1000–9999) for the pilot — the next revision will likely switch to a monotonically increasing counter once we have more than a few hundred sheets in play. For now, Tia just clicks Generate whenever operators need more stickers, prints, and hands the physical sheets to the route.
