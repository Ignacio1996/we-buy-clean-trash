Phase 11 · Security & deploy (developer appendix)

The invisible phase. No new screens, no new buttons — Phase 11 locks down Firestore and Storage with real rules, ships a reproducible pilot seed, adds the composite indexes the existing queries need, and pushes everything to production. You're mostly verifying that nothing broke after the rules flipped from default-deny to per-role access, not that a new feature works.

What you're verifying

  • Every authenticated page that worked in Phases 3–10 still loads after rules deploy — resident, operator, depot, manager, admin.
  • Direct Firestore access from an unauthenticated client is denied for every collection.
  • Direct Firestore access from a wrong-role authenticated client is denied (e.g. a resident cannot read another resident's users doc).
  • Storage reads for doorstep photos are gated to the owning resident + staff; writes are impossible from a client.
  • The pilot seed script produces the full baseline fixture (1 zone, 1 depot, admin, operator, depot worker, 5 residents) and is safe to re-run.
  • Composite indexes for redemptions, millShipments, and the second routes index are built and used by the admin/manager pages.
Setup before you start. Run npm run seed:materials then npm run seed:pilot to populate a known baseline. Then run firebase deploy --only firestore:rules,firestore:indexes,storage to push the rules + composite indexes. The index build is asynchronous — if you see a failed-precondition: index not ready error on a manager/admin page right after deploying, wait 1–3 minutes and retry. Once indexes are green you can finish with vercel --prod (or a push to main for auto-deploy).

Quick troubleshooting

What you see Likely cause What to try
PERMISSION_DENIED on an admin/depot/manager page A page is reading Firestore directly from the browser (client SDK) instead of through an API route. Rules correctly deny it. Search for @/lib/firebase/client imports in the offending page — it should only appear in auth files. Move the read to a server component or API route using @/lib/firebase/admin.
failed-precondition: index not ready on a fresh deploy Composite index is still building in Firebase. Firebase Console → Firestore → Indexes. Wait for Enabled (usually 1–3 minutes). Retry the page.
npm run seed:pilot fails with FIREBASE_ADMIN_SA not set The env file wasn't picked up. Confirm .env.local exists at the repo root and contains the full service-account JSON on a single line in FIREBASE_ADMIN_SA.
Seed says the admin email isn't in Firebase Auth Nicolas has not signed in yet on the target Firebase project. Sign in once via /login using the admin email, then re-run the seed. The script will pick up the existing Auth user and set the claim.
Test resident login fails with wrong password Someone already created the account with a different password. Either reset the password in Firebase Auth → Users, or delete the test account + re-run the seed.
Production deploy succeeds but pages 500 with "Firebase Admin not initialized" FIREBASE_ADMIN_SA is missing from the Vercel production env vars. Vercel → Project → Settings → Environment Variables. Add FIREBASE_ADMIN_SA (same value as .env.local). Redeploy.
Storage uploads still reach the bucket after the rules deploy That's fine — the app uploads through the Admin SDK server-side, which bypasses rules. The rules only gate client direct access. Verify the client isn't uploading directly by grepping for uploadBytes / ref(storage, ...) in src/. Expected count: zero.

What's not testable yet

Real account deletion, session-revocation on role change, multi-tenancy (multiple zones with non-overlapping staff), and App Check are all future work. The pilot deliberately keeps the security surface small — five roles, one zone, one depot, seed-issued staff accounts. Rotation of the Firebase service account and Vercel tokens is also manual for the pilot; the next hardening pass moves those into a secrets manager.
